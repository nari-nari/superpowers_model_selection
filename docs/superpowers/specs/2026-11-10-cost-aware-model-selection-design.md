# 料金を意識した Superpowers モデル選択仕様

作成日: 2026-11-10（Asia/Tokyo）  
状態: 仕様案。実装前。  
対象: このリポジトリの Superpowers カスタムスキル群。  
関連資料: [モデル選択指示の走査結果](../../audits/2026-11-05-model-selection-audit.md)

## 1. 目的と合意済みの方針

GitHub Copilot の AI クレジット消費を考慮し、親エージェントが作業ごとに適切なサブエージェントのモデルを選べるようにする。

ユーザーが選択した標準方針は **品質と費用の両立**。必要な能力を満たす候補を先に絞り、その候補の予想総コストを比較する。価格の安さと能力の高さを同一の順位として扱わない。

利用環境は VS Code と Copilot CLI の両方。第一版はスキル・エージェントの Markdown と参照資料の変更で構成する。MCP サーバー、独自の推論 API、料金取得サービスの導入を前提としない。

本仕様の数値初期値やファイル構成は設計上の提案であり、ユーザーが個別に指定した値ではない。

## 2. 成功条件と対象範囲

### 必須の結果

1. `cheap`、`standard`、`mid-tier`、`most capable` だけでモデルを選ぶ運用を、具体的な候補 ID・作業適性・料金を使う運用に置き換える。
2. 実装、レビュー、設計確認、調査、診断、スキルテストの派遣で同じ選択ルールを参照する。
3. 最終レビューも変更の複雑さとリスクで選ぶ。常に最高能力モデルを指定する例外を残さない。
4. 長文料金、キャッシュ、出力、再試行、引き継ぎに必要な入力を比較対象に含める。
5. 選んだモデルと実際に適用されたモデルを区別して記録する。実行結果を取得できない場合は「未確認」とする。
6. VS Code と Copilot CLI の違いを明記し、使えない設定を使えたと報告しない。
7. 見積もりのための LLM 派遣を追加しない。料金表を子全員に読み込ませない。

### 第一版の境界

- 親セッションのモデルを自動で切り替える機能は作らない。親モデルを候補に含める場合も、料金と適性を評価する。
- コンテキストは必要量の予測、情報量の削減、通常／拡張の選択方針までを必須とする。子ごとの設定適用は、環境が正式に公開する機能の範囲で行う。
- コンテキスト制御のために別 CLI セッションを起動するラッパー、SDK 実装、MCP の追加は第一版に含めない。
- 料金の定期自動更新、課金情報の自動取得、強制的な支出上限、成功確率の学習システムは作らない。
- 既存のテスト、レビュー、修正ループの回数上限を、節約のために省略・緩和しない。
- 他環境でも共通の選択方針は参照可能にするが、実機対応を保証する対象は後述の VS Code と Copilot CLI に限定する。

## 3. 構成方式

| 方式 | 特徴 | 判断 |
| --- | --- | --- |
| 役割ごとにモデルを固定 | 簡単だが、作業量・料金変更・長文料金による逆転に追従しにくい | 採用しない |
| 共通の選択スキル＋モデル一覧・料金表＋環境別手順 | Markdown 中心で、作業ごとの比較と更新箇所の集約が可能 | 採用案 |
| 外部プログラムで選択と予算を強制 | 制御は強いが、サービスやスクリプトの実装・運用が必要 | 将来の拡張 |

親エージェントが選択する。選択そのものを別のエージェントに委譲しない。料金表と方針は初回に読み、同一セッション内では版と必要な候補行を再利用する。圧縮後は方針のパスと選択記録から復元する。

相対リンクで移設可能にする。既存のユーザー共通設定や MCP 設定を変更しない。

## 5. モデル一覧・料金表のデータ要件

### 必須項目

| 区分 | 項目 |
| --- | --- |
| 識別 | 一覧内の一意なキー、表示名、モデルの版、実行環境別の正確な ID |
| 利用可能性 | 環境別の対応状況、ユーザー環境での確認状態、確認日、確認方法 |
| 作業適性 | 適用できる作業プロファイル、根拠、検証状態、既知の制約 |
| 容量 | 通常／拡張の上限、出力上限、情報源。確認できない値は `unknown` |
| 課金 | 課金方式、通貨、単位、入力・キャッシュ読み込み・キャッシュ書き込み・出力の各単価 |
| 長文料金 | 階層名、閾値、比較条件（超／以上）、閾値判定の対象、適用範囲、階層別単価 |
| 推論 | 設定可能な値と環境別 ID、未対応／不明の区別 |
| 来歴 | 公式 URL、料金確認日、内容確認日、一覧の版 |

単価は USD／100万トークンを基本とする。`0`、`not_applicable`、`unknown` を区別する。未確認のキャッシュ書き込み料金などをゼロとして計算しない。

モデル名から単価や能力を推測しない。Copilot の料金をモデル提供元 API の料金で補完しない。旧プレミアムリクエスト方式とトークン方式を混在させず、AI クレジット方式を第一版の対象とする。旧方式の環境は対象外と表示する。

### 候補と能力の具体化

- 作業プロファイルごとに、具体的な候補モデルのキーと適用条件を登録する。単なる「低／中／高」の指定で終わらせない。
- `recommended`、`provisional`、`excluded` の検証状態を区別する。これは価格順位ではなく、その作業への適用根拠の状態を示す。
- `recommended` は当該環境と作業に関する確認済みの根拠を持つ。公式説明だけを根拠にした初期候補は `provisional` とする。
- `provisional` は範囲が明確で検証手段のある通常リスク作業に使用できる。高リスク作業には、その作業に対する根拠を確認してから含める。
- 料金表への掲載と、現在のユーザーが呼び出せることは別。プラン・組織制限・実行ツールの許可を確認した候補だけを実行対象にする。
- 初期カタログには、公式に提供されている候補を記載する。実装時に最新の価格・IDを確認する。少なくとも性質の異なる2モデルの選択を対象環境で確認するまで、その環境を「動作確認済み」としない。
- 全モデルを網羅することは第一版の要件にしない。未掲載のモデルを暗黙の候補にはせず、追加時は同じデータ要件を満たす。

### 更新

価格の鮮度の目安は30日とする（初期値）。セッション開始時に版と確認日を確認し、期限超過やモデル指定エラー時に公式情報で更新を試みる。毎回の派遣で全価格を再取得しない。

取得できなければ既存スナップショットの使用と古さを一度通知し、見積もりを暫定と記録する。未知の価格を作らない。現在の候補モデル自体が利用できない、価格が欠落して比較不能、明示予算との整合が取れない場合は第10節の処理を行う。

## 6. 作業の評価とモデル選択

### 作業プロファイル

| 種別 | 判定材料 | 必要条件の例 |
| --- | --- | --- |
| 機械的な実装・修正 | 明確な仕様、局所的な変更、直接検証できる振る舞い | 指定言語と編集・テスト用ツールへの対応 |
| 統合・デバッグ | ファイル間の依存、原因の切り分け、未確定な実装判断 | 複数箇所を扱う実装・調査の適用根拠 |
| 設計・高リスク変更 | 境界の設計、並行処理、認証、データ破壊の可能性、変更の広がり | 当該リスク領域を検討できる根拠 |
| タスクレビュー・再レビュー | 差分範囲、欠陥の影響、修正前の指摘 | 差分に対応する領域知識とレビュー適性 |
| 最終レビュー | 全体の接続、共通の前提、横断的な欠陥の影響 | 全変更の関係を扱える容量とレビュー適性 |
| 調査・診断・秘匿化監査 | 読み取り中心か、量、見落としの影響 | 必要な検索・読み取り能力、監査の独立性 |
| スキルの評価テスト | 評価したいモデルと条件 | テスト対象として指定されたモデルそのもの |

ファイル数だけで決めない。小さい差分でも認証や並行処理なら要求を上げる。大量の単純置換は、検証可能なら高い推論能力を必須としない。上表の必要条件を `task-profiles.md` の具体的な候補と対応させる。

### 選択順序

1. ユーザーのモデル指定、使用禁止モデル、課金方式、明示予算を確認する。
2. 環境・バージョン・使える派遣ツール・モデル ID・能力・料金表の版を確認する。
3. 作業プロファイルとリスク、必要なツール、予測入力と出力、コンテキスト増加を整理する。
4. 利用可能性・作業適性・容量を満たさない候補を除外する。
5. 候補ごとにモデル・推論強度・コンテキスト設定を組として比較する。モデルを変えずに推論強度や入力を調整する案も含める。
6. 第7節の予想総コストで比較して選ぶ。候補が複数なら最大3件までを短く比較し、候補を絞った根拠を残す。全候補の分析文は書かない。
7. 実行に使う ID と設定を明示し、短い記録を残してから派遣する。
8. 実行環境が提供する情報で適用結果を確認する。モデル自身の自己申告だけを適用確認の根拠にしない。

ユーザーがモデルを指定した場合は勝手に別モデルへ変えない。利用不能なら理由を説明する。ルール内の通常のモデル変更について、毎回のユーザー承認は求めない。

同じ必要条件を満たし、見積もり差が不確実性の範囲内に収まる場合は、追加の引き継ぎが少なく、設定と実績が確認済みの候補を優先する。価格差を無視して最高能力モデルを選ぶための例外として使わない。

## 7. 予想総コストの扱い

単価ではなく、完了に至る一連の呼び出しを比較する。各呼び出しは履歴の増加とキャッシュ状態に応じて入力が変化する。初回入力だけにターン数を掛けて正確な費用と扱わない。

```text
呼び出しの見積もりUSD = Σ（課金対象トークン数 × 対応する単価）/ 1,000,000
一連の作業の見積もりUSD = Σ（各呼び出しの見積もりUSD）
AIクレジット見積もり = 見積もりUSD / 0.01
```

課金区分は料金表の定義に合わせる。キャッシュ書き込みと通常入力を重複・別料金として扱うかも公式定義に従い、同じトークンを誤って二重計上しない。モデル変更時の引き継ぎ入力と、必要な実装・テスト・レビューの呼び出しも比較対象にする。候補によらない共通費用は共通項として明記してよい。

### 不確実性

- 入出力・ツール呼び出し数を正確に観測できなければ範囲で示す。文字数からの推定は概算と明記する。隠れた指示やツール定義も容量を消費し得るため余裕を見込む。
- 比較可能な実績がなければ「安いモデルは2–3倍のターンが必要」などの係数や成功確率を捏造しない。
- 基本経路の費用と、1回の修正・引き継ぎを含む経路を区別して示す。実績がない場合は確率加重せず、基本経路の上側見積もりを比較の基準とし、修正経路で順位が逆転する場合はその不確実性を記録する。
- 比較可能な実績があれば、その条件・件数・観測値を根拠に再試行分を加味できる。
- キャッシュ率が確認できなければ、主見積もりはキャッシュ割引なしとする。書き込みなど未確定な課金要素は料金表に従う保守的な幅に含め、キャッシュが使えた場合の値は別に示す。
- 思考・推論トークンの課金がある場合は、公開仕様と取得できる usage の範囲で出力見積もりに含める。
- 実際に適用されると確認できた割引だけを含める。期間・環境・Autoなどの条件付き割引を、明示モデル指定にも適用できると推測しない。
- 実績費用が得られない場合は `actual_cost: unknown`。トークン数からの再計算値も請求額の実測とは区別する。

この仕組みは費用を比較するための指示であり、請求額の保証ではない。節約率の保証を受入条件にしない。

## 8. コンテキストと推論強度

### コンテキスト

作業時間やファイル数だけでは予測しない。タスク brief、コード、仕様、ツール出力、履歴の増加、必要な出力、環境側の指示を考慮する。

通常コンテキストを標準とする。予測ピークに対して上限の20%を余裕として確保する（初期値）。例えば通常上限の80%を超える見込みなら、関連箇所の抽出、ログの要約、独立タスクへの分割を先に検討する。分割によって依存関係や判断に必要な情報が失われる場合は無理に分割しない。

必要情報を収められない場合に、拡張コンテキストまたは別モデルを比較する。最大ウィンドウ、料金階層を決める入力閾値、実際の入力トークン数を別の値として扱う。上限の選択だけで料金が決まるとは仮定しない。

長文閾値をまたぐ予測では、両側の料金で計算する。全体に高単価を適用するのか、超過分だけなのか不明なら、公式情報で確認する。確認できなければ適用範囲を `unknown` として上側見積もりに高単価の全体適用を使い、正確な料金だと断言しない。

記録は `requested_context` と `effective_context` を分ける。子ごとの設定を公開していない環境では、要求を設定できた扱いにせず、`effective_context: inherited` または `unknown` とする。元の有効設定で収まるようタスクを調整する。収まらなければ当該派遣を保留し、必要な操作を一度説明する。

### 推論強度

モデル・実行環境が対応する値だけを使う。明確な機械的作業は低め、複数の仮説検証・設計判断はより深い推論を候補にするが、能力要件と費用で比較する。各プロファイルには具体的な設定値または「環境の既定」を対応させ、単に「高い推論」とは書かない。

指定できない環境では、その事実と継承／既定値を記録する。親の推論強度が子に引き継がれると一律には仮定しない。

## 9. 環境別の実行要件

VS Code を一種類の実行方式と扱わない。開始時に Local と Copilot のどちらの実行方式かを確認する。UI の名称だけでツールや設定の互換性を判断しない。

| 環境 | 仕様として要求する動作 |
| --- | --- |
| VS Code・Local | 公開されている `runSubagent` のモデル指定、またはカスタム agent のモデル設定を使う。使用可能な候補と費用階層による制限を確認し、拒否された候補は再選択する |
| VS Code・Copilot | 実際の `task` とカスタム agent 設定の対応範囲を確認する。Local の引数・モデル表示名・agent 制限設定を流用しない |
| Copilot CLI | 実際の `task` 引数、custom agent のモデル指定、ユーザー側上書き、Auto の挙動を確認する。指定が実効化されない状態は「選択を適用済み」としない |

呼び出し単位の正式なモデル指定があればそれを使う。なければ、選んだ具体的なモデルを指定したカスタム worker を使う。この worker が未登録なら、実装時のセットアップ手順で必要な Markdown を配置する。実行中に全タスクごとに agent 定義を書き換えて反映済みと仮定しない。

CLI の `modelPolicy` と VS Code の `model-policy` など、綴りや転送される項目の差を別々の例で示す。プラグイン経由の変換で無視される設定も確認対象にする。候補リストの順序は料金の自動最適化ではない。料金を比較して選んだモデルを、許可された方法で指定する。

Auto はサーバー側選択であり、本仕様の親によるモデル比較と同一ではない。現在の公式 CLI 資料には Auto 時に子のモデル設定より解決済み親モデルの継承が優先する記述があるため、バージョンと実際の挙動を確認する。適用できない場合、親セッションを無断で切り替えず、その環境では選択適用が制限されることと必要なユーザー操作を一度説明する。

他の実行環境では共通方針のみ利用し、未確認の引数を追加しない。指示の修正対象に含まれる Codex／Claude Code 向け参照にも共通方針を接続するが、今回の Copilot の単価を各社 API や別契約の料金として使わない。

## 10. 再選択・例外・予算

### 再選択

- コンテキスト不足: 入力の整理、必要箇所の追加、分割、設定変更を比較する。直ちに高額モデルへ変更しない。
- 推論・領域知識の不足: 不足能力を特定し、それを満たす候補で再選択する。「1 tier上」の固定順位は使わない。
- ツール・認証・環境の失敗: モデル変更による解決を期待せず、その原因を直す。
- レビュー範囲が小さくなった再レビュー: 縮小した範囲とリスクで再計算し、安価な候補への変更も許す。
- SDD の修正ループ: 最大5回、1–3回目の元担当再開／不可能な環境では新規派遣、4–5回目の新規担当、最終的な判定手順を維持する。4–5回目は不足能力を明記して再選択し、最高額への変更自体を目的にしない。元のモデルが十分なら、変更しない理由を記録できる。
- すでに失敗した候補へ新情報なしに戻ることで、既存の修正回数上限を実質的に増やさない。

モデル変更時は、新しい派遣・引き継ぎ・キャッシュの不確実性を再計算する。利用不能エラーを受けた候補は、そのセッションでは明示的な回復根拠が出るまで再使用しない。

### 欠落・利用不能

候補なし、モデル ID 不明、単価欠落の場合は、利用可能一覧・公式資料を先に確認する。安価そうな別モデルを無断で作らず、親モデルへの継承も成功扱いにしない。解決できなければ影響する派遣だけを保留して一度説明し、独立した読み取りや仕様整理は進める。

要求モデルと実効モデルが異なる場合は再計算する。既存の許可範囲と品質条件を満たすことを確認できる場合は、その差を記録して進められる。満たさない場合は次の派遣を止めて解消する。実行環境が途中で行った課金を取り消せるとは扱わない。

### 予算

数値予算は必須にしない。ユーザーが指定した場合だけ作業・セッション・タスクのどの範囲かと単位を記録する。上側見積もりが残額を超える場合は、分割や別候補を検討してから当該派遣について確認する。通常の選択に新しい承認フローを追加しない。

実績取得不能なら予算の消費額を正確に把握したとしない。指示上の予算判断と Copilot の強制上限は別機能であり、この変更で強制上限を提供したとは説明しない。

## 11. 記録と運用上の負担

既存の SDD ledger または作業記録に、派遣ごとに短く追記する。独立した長大なレポートは作らない。基本様式は次のとおり。

```yaml
task: task-id / role
runtime: vscode-local | vscode-copilot | copilot-cli
catalog_revision: revision
profile: concrete-task-profile
model_requested: exact-runtime-id
model_effective: exact-runtime-id | unknown
effort_requested: supported-value | default
context_requested: default | long_context | inherited
context_effective: known-setting | inherited | unknown
estimate_credits: [lower, upper] # 概算。実測値とは別
reason: 必要能力、比較した候補、費用差を一文で
actual_cost: measured-value | unknown
evidence: tool-result-or-log-reference | unavailable
```

異常がない通常の選択は既存の進捗報告に短く含める。モデル変更、長文料金への移行、価格データの欠落、指定の不適用は分かる形で報告する。全料金表や選択の思考過程を毎回会話へ貼らない。

スキルテストでは評価対象モデルを固定する。比較する variant の途中でコスト目的のモデル変更を行わず、モデル別に結果を集計する。安いモデルで高性能モデルの評価を代替した扱いにしない。

## 15. 公式仕様との接点

以下は2026-11-10確認。実装時も再確認し、今回の設計上の要求と実行環境が実際に提供する機能を区別する。

- Copilot の料金は入力・出力・キャッシュ等の使用量に基づき、長文階層や書き込み費用はモデル別に異なる。通貨換算は 1 AI credit = 0.01 USD。[Models and pricing](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)
- VS Code Local は呼び出し指定、agent 設定、Auto、親モデルの順に選択し、モデルの費用階層で制限される。[Use subagents](https://code.visualstudio.com/docs/agents/run/subagents)
- VS Code の実行方式ごとに設定と ID が異なり、editor が認識する項目でも変換時に渡されない場合がある。[Custom agent file reference](https://code.visualstudio.com/docs/agents/reference/custom-agent-file-reference)
- CLI は agent のモデル・推論強度・上書き・継承を規定し、Auto に関する制約も記載する。`--context` はセッション起動側の指定であり、子ごとの汎用フィールドがあることを意味しない。[CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference)
