- 状態: レビュー済みの仕様案。ユーザーによる本仕様書の承認前。実装・移行・実機受入は未実施。
- 対象: VS Code Local、VS Code Copilot、Copilot CLI。
- 今回の成果物: 本仕様書のみ。スキルの移設、本体の復元、ユーザー設定の変更は行わない。

## 1. 目的と前提

Superpowers の継続的な更新に追従しやすくするため、公式スキル本体を無改変で利用し、独自のモデル選択を別管理の Markdown 群から適用する。既存の料金計算・作業適性・コンテキスト・要求値と実効値の区別を再利用する。

ユーザーからは、前の会話で提示した独立レイヤー方式に基づく仕様書の作成を依頼された。本体の別途導入、下記の配置、移行判定方法は設計上の推奨案であり、個々の詳細について承認済みとは扱わない。

Markdown はエージェントへの指示であり、全派遣を機械的に捕捉するプログラムではない。仕様上の必須手順と、実行環境が強制・観測できる範囲を区別する。認識されたファイル、実際に取り込まれた指示、モデルによる遵守、ネイティブなモデル適用はそれぞれ確認する。

- [既存の実装計画](../plans/2026-11-10-cost-aware-model-selection.md)

本仕様は、既存仕様の「本体の各スキル・派遣テンプレートを書き換えて接続する」という構成・移行方式を置き換える。能力を先に満たして予想総コストを比較する方針、料金計算、コンテキスト、例外処理、評価条件固定の要件は引き継ぐ。旧仕様・計画・検証記録は履歴として保持し、旧計画を新構成の実装計画としてそのまま実行しない。構成に関する競合は本仕様を参照し、実装前に本仕様に対応した計画を作成する。

## 3. 比較した方式と採用案

| 方式 | 利点 | 負担・制約 | 扱い |
| --- | --- | --- | --- |
| 本体を別途導入し、独自レイヤーを併用 | 本体の更新と独自ルールの更新を分けられる。既存の公式配布経路を利用できる | 実際に導入された版と互換性を記録する必要がある | 初版の採用案 |
| 本体を Submodule 等で同梱し、独自レイヤーを併用 | 本体の参照コミットをリポジトリで固定できる | 取得・配布・スキル検出の管理が増える | 再現可能な同梱配布が必要になった場合の拡張 |
| 現在の各スキルへの直接変更を継続 | 現行の接続を維持できる | 上流更新ごとに多数の変更箇所を照合する | 通常方式には採用しない |

独立方式でも、上流の指示内容が変わった際の意味上の互換性確認は必要。Submodule は必須要件とせず、後から追加できるよう、独自ルールに本体のインストール先を埋め込まない。

## 4. 対象範囲と対象外

必須の変更は、独自レイヤーへの抽出、実行環境ごとの読み込み口の整備、旧改変版の有効配置からの除去、互換性記録、回帰確認、導入・解除手順の整備である。

本体は設計・計画・実装・レビュー・修正手順を担当する。独自レイヤーはサブエージェントのモデル・推論設定・コンテキスト設定の選択と適用記録を担当する。独自レイヤーを理由に、必須レビュー、テスト、レビューの独立性、修正上限を省略・緩和しない。

初版には以下を含めない。

- 本体の Submodule 化、上流更新の自動適用、自動での本体パッチ生成。
- 独自の推論 API、MCP サーバー、別 CLI 子セッションを起動するラッパー。
- 親モデルの自動変更、全体設定の自動書き換え、請求額の強制上限。
- 料金の定期自動取得、実費取得クライアント、節約率・選択遵守率の保証。
- 候補モデル、料金計算方式、能力プロファイルの同時再設計。
- Copilot の料金を流用した Codex／Claude 等の別契約向け費用最適化。

## 7. 共通入口の動作

### 7.1 適用タイミング

ルーティング指示は親の共通指示として取り込む。親がサブエージェントを新規派遣、別担当へ引き継ぎ、再派遣、モデル・推論・コンテキスト設定を変更する前に、選択手順を適用する。既存担当を再開する場合も、適用済み設定と作業条件に変化がないか確認し、変化がなければ直近の判断を再利用できる。

実装、タスクレビュー、最終レビュー、再レビュー、設計確認、並列調査、診断、スキル評価を対象とする。スキル評価の実験条件固定は通常の費用比較より優先する。派遣の必要性・許可は元の作業指示と本体の手順で決め、ルーティング指示だけを理由に派遣を増やさない。

### 7.2 入口に含める最小ルール

1. 委譲の前に、配置済みの `model-selection/SKILL.md` を明示的に読む。
2. ユーザー指定、組織・環境の利用制約、必要能力を確認した候補から、予想総コストで選ぶ。
3. 本体の `cheap`、`mid-tier`、`most capable`、段階的昇格等は、このレイヤーのモデル選択手順で具体化する。最高能力への固定や価格帯だけでの選択を根拠にしない。
4. 本体の作業手順、レビュー要件、修正上限は維持する。
5. 正式なモデル指定機構を使い、要求値と観測した実効値を分けて記録する。
6. 正式な指定ができなければ当該派遣を保留し、独立して進められる作業を続ける。

入口は詳細な料金表やプロファイルを複製しない。方針の版を持ち、参照する配置済みスキルのパスを明確にする。ユーザー固有の開発用ディレクトリやプラグインキャッシュの版付き絶対パスを原本に固定しない。

### 7.3 本体の指示との関係

ユーザーによる明示モデル指定・除外・予算・実験条件を尊重する。指定が利用不能、必要能力を満たせない等の場合は理由を伝え、勝手に別モデルへ切り替えない。

モデル選択以外の本体の指示を一括して上書きしない。「本MDが最優先」と記すだけで全環境に共通の優先順位が生じるとは扱わない。上流のモデル既定方針と独自方針が競合するケースは、実際の判断と派遣で確認する。競合を解消できない環境は、その組み合わせを対応確認済みにしない。

## 8. 読み込み・導入・解除

初版は手動で再現可能な配置手順を必須とする。インストーラーや更新スクリプトの実装は必須にしない。全プロジェクト向けの個人配置を標準とし、プロジェクト内配置を代替手順として示す。

| 環境 | 個人用共通指示の入口 | 個人用選択スキル |
| --- | --- | --- |
| VS Code Local | Agent Customizations で作成するユーザープロファイルの指示 | `~/.copilot/skills/model-selection/` |
| VS Code Copilot | `~/.copilot/copilot-instructions.md` または認識される個人用分割指示 | `~/.copilot/skills/model-selection/` |
| Copilot CLI | `~/.copilot/copilot-instructions.md` または認識される個人用分割指示 | `~/.copilot/skills/model-selection/` |

プロジェクト内では、各環境が対応する `.github/copilot-instructions.md` または `AGENTS.md` と `.github/skills/model-selection/` を使用できる。Local の指示読み込み設定、選択中の harness、CLI 自身の認識をそれぞれ確認し、VS Code の設定が CLI に自動継承されると仮定しない。

共通入口には最小ルールと明示読み込み命令を実体として含める。参照リンクの記載だけを読込証拠にしない。入口を展開する場合は `model-routing.md` を原本とし、展開先を個別の方針原本として編集しない。スキルとその参照資料は同じ版をまとめて配置する。

導入記録には方針版、原本・展開先の対応、導入前の既存内容の保存先、展開したファイル／管理ブロックの識別根拠を残す。個人PCの絶対パスやアカウント情報はローカル記録に置き、共有の互換性記録では必要に応じて伏せる。

既存の共通指示は保持し、所有範囲が分かる追加部分だけを更新・解除する。解除時は独自の展開物だけを除去・復元し、本体と他の個人用指示を残す。導入後に利用者が変更した部分へ衝突する場合は自動上書きしない。

新しい会話で、入口の取り込み、選択スキルの読込、原本と展開版の一致を確認する。利用先に旧改変本体と公式版、旧・新の選択スキルが重複して残らないことを確認する。ソースを保持するだけの旧コピーも、自動検出される場所から外す。

CLI のカスタム子エージェントへプロジェクト指示が渡るとは仮定しない。必要な規約と子の再委譲制限は brief で渡すか、当該バージョンの対応設定を使って確認する。子がルーティング一式を読み、さらに選択担当を起動する構成にはしない。

## 9. 維持する選択ロジック

既存仕様の第5～11節を、以下の条件で引き継ぐ。

- モデルID、アカウントの利用可否、作業適性、容量・出力上限を確認してから比較する。高リスクの認証・並行処理・破壊的変更・セキュリティ／秘匿化監査は、その領域の適性根拠を要求する。
- 入力、出力・推論、キャッシュ、長文階層、履歴の増加、必須レビュー、修正・引き継ぎを含めた予想総コストを比較する。未知値を無料とせず、別契約の料金で補完しない。
- 比較可能な再試行実績がなければ、基本経路の上側見積もりを基準にし、1回の修正経路を別に示す。成功確率や一律のターン倍率を作らない。
- 通常コンテキストを標準とし、予測ピークに上限の20%の余裕を確保する。80%超では情報整理や妥当な分割を検討し、必要に応じて拡張設定・別モデルを比較する。
- 料金情報の鮮度目安は30日。更新不能なら古さを一度伝える。見積もり不能な候補を、数値比較済みの候補として扱わない。
- 比較記録は代表候補最大3件。表を子へ配布せず、選択のためだけの追加派遣をしない。
- 最終レビューも実際の範囲とリスクで選び、小さな再レビューでは再評価する。修正の失敗原因がツール・認証・入力不足の場合は、原因に応じて対処する。
- 修正回数・担当の再開／交代等は対象本体のワークフローに従う。基準版での最大5回を節約目的で緩和しない。上流で手順が変われば互換性確認で差分を扱う。
- 実験の評価モデル・設定は variant 間で固定する。費用比較のために評価条件を変えない。
- 数値予算はユーザー指定時だけ適用する。上側見積もりが残額を超える場合に当該派遣の代案を検討し、必要な確認を行う。通常の選択には承認を追加しない。

## 10. ネイティブ指定と確認

正式な呼び出し単位のモデル指定を優先する。それが使えない場合に限り、確認済みIDを指定したカスタム worker を利用する。worker は必要になった環境だけに追加し、認識・許可ツール・モデル適用を確認する。プレースホルダー入りの定義を有効化しない。

実際のツールスキーマとクライアントの版を確認し、Local の引数やID、CLI の agent フィールドを別環境へそのまま転用しない。Auto、ユーザー設定、料金階層による拒否、プラグイン変換による設定欠落も確認する。モデル設定が認識されることと、子へ転送されることを分ける。

| 状況 | 必須の扱い |
| --- | --- |
| 正式なモデル指定がない | 対応方法を調べ、解決不能なら当該派遣を保留。プロンプト内のモデル名で代用しない |
| 正式な指定はできるが実効IDを観測できない | `unknown` を残す。ほかの制約を満たせば作業は続行可能だが、適用確認の受入は未検証 |
| 要求と実効が不一致 | 能力・許可・費用を再評価。満たさなければ次の当該派遣を保留。実行済みの課金は取り消せない |
| 子のコンテキスト／推論設定を指定できない | 確認できた継承／既定値または `unknown` を記録。容量を確認できず入力が収まる根拠もなければ当該派遣を保留 |
| ネイティブ指定が拒否された | 許可候補で再評価。指定を省略して親モデルに継承させ、成功と記録しない |

実効値の根拠はツール結果・メタデータ・ログ・UI等の独立した情報とする。モデル自身の名乗りは根拠にしない。未観測と、要求が不適用だったことを確認できた状態を区別する。

## 11. 記録と互換性

通常の選択は既存 ledger／作業ログに短く追記し、毎回独立した長文レポートを作らない。異常、変更、未適用、長文課金への移行は分かる形で伝える。

```yaml
task: task-id / role
runtime: vscode-local | vscode-copilot | copilot-cli
routing_revision: policy-revision
catalog_revision: catalog-revision
superpowers_revision: observed-revision | unknown
runtime_version: observed-version | unknown
profile: concrete-task-profile
model_requested: exact-runtime-id
model_effective: exact-runtime-id | unknown
effort_requested: supported-value | default
effort_effective: observed-value | unknown
context_requested: default | long_context | inherited
context_effective: observed-value | inherited | unknown
estimate_credits: [lower, upper] # または unknown
reason: 必要能力・候補比較・費用の判断を短く記載
actual_cost: measured-value | unknown
evidence: independent-result-or-log-reference | unavailable
```

同一セッションで変わらない版・環境情報は共通記録への参照で省略できる。圧縮後は方針のパス・版と直近の判断を復元する。見積もり、使用量からの再計算、実際の請求額を区別する。

互換性は本体版、独自方針版、実行環境／クライアント版の組み合わせで記録する。取得元・版の確認根拠、実際に読み込んだソース、ケース結果、独立したモデル情報、既知の制約を記載し、次を分ける。

| 検証状態 | 意味 |
| --- | --- |
| 未検証 | 当該構成の確認なし、または必要な証拠が不足 |
| 文書・シミュレーション確認済み | 静的確認／架空データ／読み取り専用の判断確認のみ |
| 実機確認済み | 記録した環境と版で、必要なネイティブ受入条件を満たした |
| 不適合 | 競合、拒否、設定不適用等が再現し、必要条件を満たさない |

VS Code Local、VS Code Copilot、CLI は別々に判定する。本体の版を取得できなければ `unknown` と確認範囲を残し、版固定の互換性を証明したとしない。全体の移行完了は3方式の必須条件が揃った場合とし、一部だけ確認済みなら対応範囲を限定して表示する。

## 12. 上流更新と最小パッチ

本体の更新は公式の導入経路で行い、独自レイヤーは本体やキャッシュを書き換えない。更新の自動検知は初版に含めず、導入・更新時と、新しいセッションで確認できる範囲で版を照合する。版が変わった場合は互換性を未検証として扱い、必要な代表ケースを再確認する。全作業を一律停止せず、確認不能・不適合な派遣に限定して対処する。

確認対象は、派遣方法、モデル選択の指示、役割・レビュー要件、担当交代・修正上限、補助スクリプトの呼び出し方。文字列検索だけで判断せず、モデル方針に競合する新しい表現も読む。本体の版が変わっても価格表まで書き換えることを必須にしない。

独立指示と正式な環境設定で解消できない競合が実機で再現した場合に限り、最小パッチを例外案として扱う。再現ケース、試した無改変方式、必要な変更、対象版、撤去条件を仕様変更として記録する。

例外を採用する場合も、原本と派生物を区別し、別のパッチファイルで管理する。上流更新時に適用可否と挙動を確認し、適用不能ならそのパッチの利用を停止する。パッチを使う構成を「本体無改変方式の受入完了」とは記録しない。

## 13. 移行の順序と戻し方

1. 現在の実装コミットと作業差分を保存し、旧配置・設定の復元方法を記録する。
2. 比較対象にする公式の取得元・版・コミットを特定し、本体の原本を用意する。原本の出自が未確定なら、復元完了としない。
3. 独自6ファイルを抽出し、管理用配置、参照関係、共通入口、互換性記録を整備する。算術・候補判定の判断結果を維持する。
4. 検証用の利用先で、無改変本体と独自レイヤーを配置する。26ファイルの独自変更と35項目の旧指示がどこで扱われるか照合する。
5. 重複検出、文書・架空データ確認、競合シミュレーション、環境別の実機確認を行う。旧検証結果をそのまま新構成の成功に転記しない。
6. 合格した方式から利用先を切り替える。旧改変スキルはGit履歴等に保存し、自動検出される配置から外す。
7. READMEと検証記録に利用可能な方式と未検証範囲を反映する。3方式が揃わなければ、全体の移行完了とは報告しない。

不適合があれば、記録した独自の展開部分を解除・復元する。旧改変構成へ戻す場合は、公式版との同時読み込みを解消したうえで切り替え、両構成を混在させない。ユーザー独自の設定変更を巻き戻す手段として利用しない。

## 14. 受入条件

以下は将来の実装・移行の受入条件であり、本仕様作成時の実行結果ではない。既存AC01～AC20の能力・費用・例外・評価条件を維持し、旧AC17の各呼び出し元更新は本仕様の分離・指示対応へ置き換える。重複する確認は証拠を参照し、同じ実機呼び出しを不要に繰り返さない。

文書・架空データ確認では、静的リンク、原本との差分、JSONデータの整合性、料金計算、短い判断シナリオを確認する。競合確認は原本の指示を残した状態で行い、原本側の最高能力指示を取り除いた入力を無改変方式の検証に使わない。

実機確認は対応するアカウント・環境で行う。モデルの自己申告、カタログにIDがあること、別サービス上のシミュレーションをネイティブな適用証拠にしない。実機アクセスがなければ文書実装までを記録し、実機条件と移行完了は未検証のまま残す。
