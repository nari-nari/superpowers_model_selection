# Delegated Model Routing

routing_revision: 2026-11-11.2

This is the parent's model-selection policy for delegated work in this session. Apply it to implementation, task/final/re-review, design checks, research, diagnosis and skill evaluation. It does not authorize new delegations or replace the workflow's task, security, review, independence or repair requirements.

1. **Read before dispatch.** Read `model-selection/SKILL.md` at the verified `model_selection_skill` binding supplied with this instruction. Resolve a missing binding or file before the affected dispatch. Retain the policy path/revision and catalog revision for reuse and compaction recovery. On resuming a worker, reuse its last decision only while task conditions and applied settings remain unchanged.
2. **Respect constraints and qualify.** Honor explicit user models, exclusions, scoped budgets and organization/runtime restrictions. Identify the billing contract and use its applicable catalog; included ChatGPT usage, Codex credits, Copilot credits and API billing are distinct. Fix an experiment's designated evaluator/settings across variants. First qualify candidates for the task's actual risk, tools and capacity, then compare predicted completion costs using `model-selection`. An unavailable, unqualified or unpriced candidate is not a cheap fallback. An explicitly authorized fixed-model capability probe is recorded as an experiment, never as successful cost optimization.
3. **Resolve model defaults through this policy.** Superpowers' model-tier defaults (`cheap`, `mid-tier`, `most capable`, tier escalation and inherited-model defaults) are concretized by this selection procedure. A final review has no automatic highest-capability exception. Diagnose missing inputs, reasoning deficits and tool failures separately. Keep all workflow-required reviewers, independent roles, worker-change rules, tests and repair limits.
4. **Apply a supported selection.** Use the actual runtime adapter and an explicit native model argument or a verified model-pinned worker. A model name inside a prompt is not a model setting. Parent model changes, new CLI child sessions and invented parameters are not routing mechanisms. If no supported route exists, hold only that dispatch and continue independent work.
5. **Verify and record.** Record requested and independently observed effective model/effort/context separately in the existing work log, with policy/catalog/runtime/upstream revisions, cost estimate and evidence. Model self-identification is not evidence. Accepted explicit routing with unobservable effective values may proceed within the other constraints, but stays `unknown` and native acceptance remains unverified. Recheck capability, permission and cost after a mismatch; hold the next affected dispatch if it fails those checks.
6. **Keep the workflow intact.** The parent owns selection. Give workers only their task brief, required artifacts/conventions and applied settings; workers do not route more workers. Missing prices, budget overruns or unsupported settings affect only the relevant dispatch. Routine eligible selections need no additional approval; unresolved explicit user constraints must be explained rather than silently substituted.

Deployment must append one `model_selection_skill: <verified installed SKILL.md path>` line inside the managed instruction block. The deployed path must exist and its bundle must match the recorded source version. A link, discovered skill name or this undeployed source file alone is not proof of inclusion. Instruction precedence differs by harness; verify conflict cases against the unchanged upstream, and record noncompliance rather than claiming this Markdown enforces runtime behavior.
